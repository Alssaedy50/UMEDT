# UMED-2 Data Validation and Security Architecture

## 1. Multi-Layer Integrity & Security Model
Data entering UMED-2 is verified across 4 distinct security barriers:
1. **Physical Integrity (SHA-256 Checksum)**:
   - Verifies that file bytes have not suffered bit-rot or network corruption.
2. **Provenance & Source Authenticity (ECDSA-P256-SHA256 Digital Signature)**:
   - For signed packages, verifies the release was published by an authorized medical authority.
   - Unsigned packages generated by users are permitted under an explicit "Unsigned User Package" classification.
3. **Storage Contract Compatibility (Schema Versioning)**:
   - Verifies `schema_version == 2` and `minimum_app_version <= 2.2.0`. Incompatible packages are rejected before decompression.
4. **Content Validation & Sanitization**:
   - Strips malicious control characters, restricts file depth to $\le 4$ levels, and bounds decompression ratios ($\le 80:1$).

## 2. Zero Private Key & Secret Leakage
- Private signing keys are never shipped with the application.
- API tokens (Cloudflare, Gemini) are never baked into client bundles or APK assets.
- Build verification tests (`scripts/verify-release-readiness.ts`) automatically scan output bundles for leaked private keys and secrets.
